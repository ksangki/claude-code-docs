## 왜 멀티에이전트인가

**문제**: 한 대화에서 모든 작업을 순차 처리하면
- 컨텍스트 오염
- 지연 시간 증가
- 특화 어려움

**해결**: 작업을 독립 에이전트로 **분할** → 병렬 실행.

**효과:**
- 독립 워크스트림 **동시 진행**
- 특화된 시스템 프롬프트로 **전문화**
- 부모 컨텍스트 **보호**

---

## 서브에이전트 작동 방식

Claude가 `Agent` 도구 사용 → 새 Claude 인스턴스 시작.

**각 에이전트의 소유물:**
- **새 컨텍스트 윈도우** (fork가 아닌 한)
- 에이전트 타입별 **특화 시스템 프롬프트**
- 자체 **도구 권한** (타입별 설정 가능)
- **추가 서브에이전트 스폰** 가능 (중첩 제한)

부모는 에이전트 완료까지 대기 (또는 백그라운드면 다른 작업 계속) → **결과를 단일 메시지로 수신**.

---

## `Agent` 도구 파라미터

Claude가 **필요 판단 시** 호출. 직접 호출하는 것이 아님.

| 파라미터 | 설명 |
|---|---|
| `description` | 3-5단어 요약 (UI 표시용) |
| `prompt` | 에이전트에 대한 **전체 작업 설명** |
| `subagent_type` | 특화 타입 (선택, 기본 범용) |
| `run_in_background` | 비동기 실행 여부 |
| `isolation` | `"worktree"` → 격리된 git worktree |

터미널에서 에이전트 스폰을 **자체 진행 표시기**와 함께 확인 가능.

---

## 언제 스폰하는가

Claude가 자동으로 판단하는 패턴:

- **독립적 병렬 작업**
  - 문서 업데이트 + 테스트 작성 동시
- **특화 작업**
  - 보안 감사용 **코드 리뷰어 에이전트**
- **장시간 실행 작업**
  - 다른 작업 중 **백그라운드 리서치**
- **격리된 탐색**
  - 메인 컨텍스트 오염 없이 **솔루션 시험**

---

## 명시적 요청 예시

**Claude에게 직접 요청 가능:**

```
linter와 test suite를 병렬로 실행해줘.
```

```
세 경쟁 라이브러리가 이 문제를 어떻게 처리하는지
별도의 에이전트로 조사한 후 결과를 요약해줘.
```

```
보안 에이전트가 이 코드 변경의 보안 영향을 검토하는 동안
기능 구현을 계속해줘.
```

> "**병렬로**" 요청 시 → 여러 Agent 호출을 **단일 메시지**로 발송해 동시 시작.

---

## 포그라운드 vs 백그라운드

**포그라운드 (기본)**
- Claude가 완료까지 **대기**
- 결과가 다음 작업에 **필요한 경우**
- 순차 의존성 있는 작업

**백그라운드**
- **비동기 실행** (`run_in_background: true`)
- Claude가 시작 후 **다른 작업 계속**
- 완료 시 **알림 수신**

```
다음 기능을 구현하는 동안
통합 테스트를 백그라운드에서 실행해줘.
```

---

## ⚠️ 백그라운드 에이전트 주의

**출력 파일을 직접 확인 요청하지 말 것.**

Claude는 **자동으로 완료 알림**을 받음 → 폴링/파일 확인 불필요.

**올바른 패턴:**
- 백그라운드 시작 → 다른 작업 진행
- 완료 알림 수신 → 결과 처리

**잘못된 패턴:**
- `sleep 10 && cat output.log` → 불필요, 반복, 컨텍스트 낭비

---

## 코디네이터 모드

**Claude가 모든 구현 작업을 서브에이전트에 위임** → 계획·라우팅·종합에 집중.

**적합한 경우:**
- 매우 큰 작업
- 명확히 분할 가능한 서브 문제
- 병렬화 이득이 큰 경우

**주의:**
- 서브에이전트 **프롬프트 품질**이 결과 좌우
- 종합 단계에서 결과들의 **일관성 보장** 필요

---

## 컨텍스트 격리

**각 서브에이전트는 깨끗한 컨텍스트 윈도우로 시작.**

**의미**:
- 부모의 대화 기록 **자동 상속 안 됨**
- 에이전트 프롬프트에 **전체 작업 설명 + 배경** 필요
- 메인 세션이 오염되지 않음

**장점**: 병렬 에이전트가 서로의 토큰 예산을 침해하지 않음.
**단점**: 프롬프트 작성 부담 ↑

---

## 영속 에이전트 메모리

일부 에이전트 타입은 **호출 간 영속 메모리**.

| 범위 | 경로 |
|---|---|
| 사용자 | `~/.claude/agent-memory/<agent-type>/MEMORY.md` |
| 프로젝트 | `.claude/agent-memory/<agent-type>/MEMORY.md` |
| 로컬 | `.claude/agent-memory-local/<agent-type>/MEMORY.md` |

**활용**: 반복 호출되는 에이전트가 **이전 학습을 재사용** (예: 코드 리뷰어의 과거 지적 사항).

---

## Worktree 격리

`isolation: "worktree"` → 에이전트에게 **자체 git worktree** 제공.

**효과:**
- 저장소의 **격리된 복사본**
- 에이전트 변경 사항이 **내 작업 디렉토리에 영향 안 줌**
- 내가 **병합 전에 검토** 가능

```
내가 변경 사항을 검토하고 병합할 수 있도록
격리된 worktree에서 이 기능을 구현해줘.
```

**사내 활용**: 실험적 구현, 큰 리팩터링, 병렬 기능 개발.

---

## 효과적인 에이전트 프롬프트

**핵심**: 서브에이전트는 부모 대화 컨텍스트 **없음**.

좋은 프롬프트의 구성:
1. **달성하려는 것과 이유**
2. **관련 파일 경로, 함수 이름, 데이터**
3. **에이전트가 보고해야 할 내용** (형식, 길이, 답해야 할 질문)
4. **에이전트가 하면 안 되는 것** (범위 제약)
5. **이미 시도했거나 배제한 것**

---

## 나쁜 vs 좋은 프롬프트

**나쁨:**

```
버그를 수정해줘.
```

**좋음:**

```
src/services/user.ts:247의 UserService.getProfile()에 있는
null 참조 버그를 수정해줘.

사용자에게 연관된 프로파일 레코드가 없을 때 버그 발생 —
getProfile()이 profile이 null인지 먼저 확인하지 않고
profile.preferences를 호출함.

null 체크를 추가하고 기본 설정 객체
{ theme: 'light', notifications: true }를 반환하세요.

그 후 npm test를 실행해 수정 사항이 기존 테스트를 통과하는지
확인하세요.
```

---

## 제한사항

- 서브에이전트는 기본 **`acceptEdits` 모드**
- **Escape** → 부모 턴 취소, 백그라운드 에이전트 **취소 안 됨**
  - 작업 패널에서 **명시적 취소** 필요
- 서브에이전트는 **다른 에이전트 스폰 불가** (팀 로스터 플랫)
- **포크 에이전트**는 자신을 다시 포크 불가
- 에이전트 결과는 부모에 반환 전 **100,000자로 제한**
